# Introduction

Rudel manages WordPress sandboxes and apps as request-selected overlay environments.

One host WordPress installation stays in place. Rudel creates environment records, clones the host WordPress tables into environment-specific prefixes, copies the selected active theme into an environment-owned theme root, and resolves the active environment during bootstrap.

The runtime selection boundary is explicit:

- no environment selector means WordPress boots as the host
- `X-Rudel-Environment` selects an environment for HTTP requests
- `rudel_environment` selects an environment by cookie
- `RUDEL_ENVIRONMENT` selects an environment for WP-CLI
- mapped app domains can select app environments

## Two environment types

**Sandboxes** are disposable environments for change work, QA, debugging, demos, migrations, and agent-driven tasks.

**Apps** are durable environments that keep domain metadata, backups, deploy history, worktrees, and long-lived lifecycle state.

Both use the same overlay runtime. The difference is lifecycle intent, not a different WordPress substrate.

## Runtime shape

Rudel keeps three layers clear.

**WordPress host** is the shared process, core install, plugin directory, upload directory, and user table source.

**Environment overlay** is the selected table prefix plus copied active theme. A selected environment gets table names like `wp_a4nmv7_options` and a theme root like `wp-content/rudel-environments/alpha-1234/themes`.

**Rudel runtime records** are the operational source of truth. Rudel stores app identity, environment identity, domain mappings, worktrees, deployment history, and policy metadata in host WordPress MySQL tables.

Rudel does not require multisite. Rudel does not use SQLite. Rudel does not use JSON as runtime configuration.

## What Rudel adds

- environment creation and destruction
- app creation from the same overlay model
- app-derived sandboxes
- snapshots for sandboxes
- backups, deploys, and rollback for apps
- PHP-native Git workflows through Pitmaster
- policy metadata such as owner, labels, protection, and expiry
- DB-backed registry access inside and outside WordPress

## Requirements

- PHP 8.2 or later
- WordPress 6.4 or later
- the normal WordPress MySQL/MariaDB database
- write access to `wp-config.php` during bootstrap installation
